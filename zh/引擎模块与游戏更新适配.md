# 引擎的模块划分与游戏更新适配（2026-11-08）

用户：“好好梳理一下我们的引擎……近期可能迎来一次游戏版本更新，会有卡牌或者遗物的修改以及增删，部分观测可能需要变，引擎接口可能也要重新修改。
请你把我们的引擎做好一个很好的模块化设计，使得我们能够迅速适应新版游戏更新，从而快速地在新版游戏中使用我们的引擎继续进行训练。”

本文分两部分：
- 引擎现在的模块划分：第一至三节；
- 游戏更新时按什么步骤适配：第四至七节。

所有改动在 `engine-modular` 分支上分步提交，每一步都用 `tools/engine_equal.py` 做逐字节对拍，确认故障机器人、储君、静默猎手、铁甲战士、亡灵契约师的帧都没变（第八节）。

## 一、引擎的组成

| 部分 | 位置 | 作用 | 游戏更新时 |
|---|---|---|---|
| 无头引擎 | `engine/Sts2Headless/` | 直接运行游戏自带的 `sts2.dll`，不重写规则：启动顺序（Bootstrap）、界面与 Godot 的替身（GameShim、GodotShim、FakeScreens、UiCallStubber）、保真补丁、决策流程（RunSession、UiFlows、RewardsFlow）、协议（Server） | 补丁目标、私有成员可能改名（第三节）；游戏规则本身不用改 |
| 观测编码 | `engine/Sts2Headless/Engine/Observation.cs` + `Engine/Obs/` | 局面 → 定长数组（格式见 `观测格式.md`），无头引擎与实机桥接模组共用 | 按游戏代码写的算法、内容表要复核（第二节、第六节第 3 步） |
| 兼容层与自检 | `Engine/Compat/GameCompat.cs`、`SelfCheck.cs` | 所有按名字找的游戏成员都经它登记；`selfcheck` 一次查全 | 更新后第一步就跑（第四节） |
| 词表与内容目录 | `engine/catalog/vocab.txt`、`engine/catalog/<版本>/catalog.json` | 词表只追加不重排；内容目录给内容先验与课程用 | `catalog` 命令追加新内容、导出新目录 |
| 实机桥接模组 | `engine/Sts2Bridge/` | 在真实游戏里编码观测、执行动作（直播会话维护） | 用同一份观测编码；`engine/Directory.Build.targets` 替它把 `Obs/`、`Compat/` 编进去 |
| sts2-sim 服务 | `engine/Sts2SimServe/` | 搜索用的 sts2-sim 镜像与移植版编码器（ObsPort，直播会话维护） | sts2-sim 自己要跟新版规则；ObsPort 要跟观测格式 |
| Rust 引擎 | `rust-engine/` | 重写的规则（现阶段不用于训练） | 不在本文范围 |
| Python 端 | `python/sts2env/`（协议、环境、`gamever.py`）、`python/sts2rl/`（训练） | 帧解析、内容先验、课程 | 格式表（`protocol.format_for`）、内容先验按新目录重建 |
| 局面复制 | `engine/Sts2Headless/Engine/Clone/` | 在决策点存下完整局面、反复恢复（原地快照），搜索与训练时推演用；协议见 `Server.cs` 顶部 | 跑 clone-test 与跨进程验收（第六节第 10 步）；改 `ClonePolicy.cs` 的叶子与根 |

## 二、观测编码的模块（`Engine/Obs/`）

Observation 是分部类。原来 2,631 行的一个文件，现在按区域和角色拆成下面这些文件。拆分是纯搬移，帧逐字节不变：

| 文件 | 内容 |
|---|---|
| `Observation.cs`（297 行） | 记录类型与区域的枚举、编排（`Encode`：全局 → 战斗中 / 战斗外 → 遗物与药水 → 地图与路线、小游戏、选牌说明 → 看得到的对象 → 候选 → 整局信息 → 头部）、`Emit`、`Ref`、`Serialize` |
| `Obs/Format.cs` | 格式版本常量、按角色定版本（`FormatFor`）、本帧的版本门控（`V20`、`V21`、`V22`） |
| `Obs/Header.cs`、`Obs/Candidates.cs` | 头部 34 项；候选的 12 个特征 |
| `Obs/Cards.cs`、`Obs/Creatures.cs`、`Obs/Powers.cs`、`Obs/Relics.cs` | 卡牌（数值预览、X 费段数、附带记录）、生物与意图、招式预告、能力的通用读法、遗物与药水 |
| `Obs/EndTurn.cs` | 回合结束预演（玩家与敌人的 16–19、候选 10 的“假设”版本 `LossAfterFn`；格式 22 的 `Loss22`：奥斯提、反伤、亡灵精通） |
| `Obs/Damage.cs` | 伤害与掉血的公用算法（`HitDmg`、`SeqHpLoss`、`FoeHpLoss`、`PlayCount`、`ShellLeft`） |
| `Obs/CombatStats.cs` | 战斗计数记录（子类型 0、1、3） |
| `Obs/Riders22.cs` | 格式 22 的出牌附带效果 |
| `Obs/Map.cs`、`Obs/Events.cs`、`Obs/RunInfo.cs`、`Obs/Privileged.cs` | 地图与路线摘要；事件、休息处、小游戏、选牌说明；出怪池、预生成内容、本幕历史；特权的抽签推演 |
| `Obs/Characters/` | 各角色专属的内容表与算法：Defect（充能球）、Regent（星统计、已知牌堆顶）、Silent（毒、刀刃陷阱、出牌附带效果）、Ironclad（自伤、消耗）、Necrobinder（召唤、牺牲、灾厄） |

### 加一个新的观测格式

以格式 22 为例：
1. 在 `Obs/Format.cs` 加常量、门控变量（`V22`），并在 `FormatFor` 里登记哪些角色用它。
2. 在 `Observation.Encode` 开头、结尾设、清门控。
3. 新内容一律写成 `if (V22) …`，放进对应区域的文件或角色文件。
4. Python 端改 `protocol.py` 的 `FORMAT_BY_CHARACTER`、`COMPAT_VERSIONS`。
5. 写 `观测格式.md` 的一节。
6. 用 `tools/engine_equal.py` 确认别的格式逐字节不变（可强制 `--obs-format` 做门控核对），再写一个对真实结果的核对工具（照 `tools/obs_v22_check.py`）。

布局（头部 34、记录 20、候选 12 列）从格式 19 起没变，新内容都放在原有的列、新的区域或新的记录里，网络不用改。

### 和游戏代码直接相关的部分（游戏更新时要复核的“接触面”）

- **游戏的钩子**：只在几个公用函数里调用。
  - 伤害：`HitDmg` → `Hook.ModifyDamage`；
  - 掉血：`SeqHpLoss`、`FoeHpLoss`、`PoisonNext`、`SelfHpLoss` → `Hook.ModifyHpLost`；
  - 格挡：`AfterimageBlock` → `Hook.ModifyBlock`；
  - 打出次数：`PlayCount` → `Hook.ModifyCardPlayCount`；
  - X 值：`XHits` → `Hook.ModifyXValue`；
  - 其余（ShouldDraw、ShouldFlush、ModifyHandDraw、ModifySummonAmount、ModifyPowerAmountGiven / Received 等）各只有一两处。

  钩子签名变了，编译会报错，改这几个函数即可。
- **按游戏代码写死的规则**：都在角色文件和少数几处，写成表：
  - X 费、固定两段的攻击（`Cards.cs` 的 `XHits`）；
  - 生成充能球的牌（`Defect.cs` 的 `OrbChannels`，按类名）；
  - Boss 招式给的力量与格挡（`Creatures.cs` 的 `MoveGains`，按招式 ID）；
  - 回合结束生效的能力与遗物（`EndTurn.cs` 的两个 switch）；
  - 自伤牌、另外消耗牌的张数（`Ironclad.cs`）；
  - 当场召唤、会杀奥斯提的牌（`Necrobinder.cs`）。

  用 `typeof` 写的，游戏删掉这个类时编译报错；按名字写的，由 `selfcheck` 核对（第四节）。
- **私有成员的反射**：都经 `GameCompat` 登记（第三节）。

## 三、游戏版本兼容层（`Engine/Compat/GameCompat.cs`）

引擎依赖游戏的私有字段、属性、方法和 Harmony 补丁的目标，原来散在十几个文件里。新版游戏把哪个改了名：
- 补丁的目标找不到，引擎启动时报第一个错就停，后面还有几个只能一个一个修；
- 反射找不到时多半是 `null`，观测里那一项静默地编成 0，要等某个局面碰巧走到才会被发现。

现在所有按名字找游戏成员的地方都经 `GameCompat`：

- `GameCompat.Field / Property / Getter / Method(类型, 名字, 用途)`：返回值与原来的 `AccessTools`、`Type.GetXxx` 完全相同，同时登记“哪个成员、做什么用、找到没有”。
  找不到也有退路的（界面单例的后备字段）用 `OptionalField`，不算问题。
- `GameCompat.Patch(harmony, 目标, 描述, prefix/postfix/finalizer)`：
  - **正常模式**：目标找不到时照旧抛异常、引擎启动失败，与原来一样，训练不会带着缺了补丁的引擎跑；
  - **自检模式**：登记下来，跳过，继续装后面的。
- `GameShim.Install` 的每组补丁（保真、无头修补、假界面、已知牌堆顶……）在自检模式下各自捕获异常。所以一组出错不影响后面各组的检查。
- `GameCompat.CardNames(用途, 类名...)`：按类名写的内容表（`OrbChannels`）登记，自检时核对类名还在不在。

登记的成员：
- 无头引擎：观测编码里的 13 处反射，补丁 60 处，开幕快照、内容目录、预知记录里的反射；
- 实机桥接模组：编译同一份 `GameCompat`，观测编码在实机上的反射也经它。

## 四、自检：`dotnet Sts2Headless.dll selfcheck`

```bash
cd engine/Sts2Headless && dotnet build -c Release -o ../../.cache/eng && cd ../..
dotnet .cache/eng/Sts2Headless.dll selfcheck 2          # 每个角色 2 局整局 + 9 场战斗；--all 连找到的也列出
```

约 10 秒，只读（不写词表、不写文件）。退出码：有问题为 1。查四样东西：

1. **补丁目标与私有成员**：以自检模式装补丁，再把引擎里所有类型的静态初始化跑一遍（反射字段都在那里），列出 `GameCompat` 登记里找不到的。
2. **按名字写的内容表**：OrbChannels 的卡牌类名；MoveGains 的（怪物，招式 ID）在新版怪物的招式表里还在不在。
3. **词表**：
   - 代码里直接写的词表键（`STAT:STARS`、`CARDMOD:*` 等）在不在；
   - 当前游戏应有的键（模型、事件选项、休息处、奖励、地图节点、意图、招式）有哪些不在词表，这些是新内容，要跑 `catalog` 追加；
   - 词表里有、游戏里没有了的模型键，是删掉或改名的内容。词表只追加不删，旧 ID 留着。
4. **冒烟**：五个角色各打几局整局，加第一、二、三幕的普通战、精英战、Boss 战，随机出牌、每步都编码观测，数异常、卡住和新出现的词表外键。

**现在（v0.111.0）的结果**：
- 登记 145 处（补丁 60），找不到 0 处，另有可选的 3 处；
- 词表应有的键 2,262 个，都在；
- 五个角色冒烟异常 0、卡住 0；
- 冒烟时遇到 7 个词表外键：开局涅奥的 6 个选项，加 `MOVE:TERROR_EEL.STUNNED`。这是原有的情况，猎人观测调研第三节写过。加进词表会改变故障机器人、储君的帧，所以没加，留给换版本时一并处理。

**反向核对（证明它真能查出问题）**：在一份引擎副本里故意改坏 5 处：
- 凯撒蟹朝向的私有字段；
- 污秽药水的补丁目标；
- 已知牌堆顶补丁的 `CardPile.Clear`；
- OrbChannels 里加一个不存在的类名；
- 知识恶魔的招式 ID。

`selfcheck` 一次列出全部 5 处（补丁的两处同时列出“方法找不到”和“补丁目标找不到”），退出码 1；同一份副本用 `serve` 启动，照旧在第一个缺失的补丁处报 `MissingMethodException` 停下。

## 五、游戏版本只写在一个地方

`engine/game_version.txt`（现在是 `v0.111.0`）。读它的地方：

- **MSBuild**：`engine/Directory.Build.props` 读出版本，设 `Sts2GameDir = ~/.local/share/sls2/game/<版本>`，各项目默认用它。
  - 命令行 `-p:Sts2GameVersion=v0.112.0` 换版本，`-p:Sts2GameDir=...` 直接指定目录（远程部署脚本就是这样）。
  - 没有 HOME（Windows 上直接编）时不设，沿用各 csproj 自己的默认。
- **引擎**：编译时把版本写进运行时配置（`Sts2GameVersion`），`catalog` 命令默认按它命名内容目录。
- **Python**：`python/sts2env/gamever.py`（`GAME_VERSION`、`catalog_path()`、`game_dir()`、`localization_dir()`）。
  - `sts2rl.catalog.Catalog` 与内容先验（`sts2rl.content.CATALOG_VERSION`）的默认版本取它。
  - 换版本后内容先验按新目录重建：新内容有了先验，改了数值的条目先验跟着变。
- **远程脚本**：`tools/remote/hosts.sh` 的 `GAME_VER`、`pack.sh` 与 `setup.sh` 的 `STS2_VERSION` 默认取它。

以上每处在文件不在时都退回 `v0.111.0`，不会因为部署漏了一个文本文件起不来。

**还写死 v0.111.0 的地方**：看板、直播覆盖层、回放查看器、储君启动脚本等工具，有的是别的会话正在改的文件，这次没动。换版本时用下面这条命令找出来，改成读 `sts2env.gamever`：

```bash
grep -rn "v0\.111\.0" --include=*.py --include=*.sh tools python | grep -v "gamever.py\|game_version.txt"
```

当时的清单：
- `tools/dashboard.py`（本地化路径、社区选牌统计文件名、内容目录）；
- `python/overlay.py`（本地化路径、内容目录；直播会话的文件）；
- `tools/replay_viewer.py`、`tools/gen_card_pinyin.py`、`tools/calib_intervene.py`、`tools/ability_report.py`；
- `tools/remote/retest.sh`、`tools/remote/unsolved_probe.sh`（内容目录）；
- `tools/remote/regent/start.sh`（社区选牌统计文件名；储君会话的文件）；
- `tools/fetch_card_stats.py`（默认的统计分组）；
- `engine/Sts2Bridge/Sts2Bridge.csproj`：Linux 下被 `Directory.Build.props` 覆盖，只在没有 HOME 时起作用。

## 六、游戏更新的适配步骤

1. **拿到新版文件**（只放本机与租用机，不入库；同 README“准备”一节）：

   ```bash
   V=v0.112.0
   G="/mnt/c/Program Files (x86)/Steam/steamapps/common/Slay the Spire 2"
   mkdir -p ~/.local/share/sls2/game/$V
   rsync -a "$G/data_sts2_windows_x86_64/" ~/.local/share/sls2/game/$V/
   python3 -I tools/extract_pck.py "$G/SlayTheSpire2.pck" ~/.local/share/sls2/game/$V/res localization/eng/ localization/zhs/ localization/completion.json
   ```

   - 再用 ilspycmd 把 `sts2.dll` 反编译到 `~/.local/share/sls2/decompiled/$V/`，按命名空间分目录，与旧版相同（M0 验证报告用的是 ilspycmd 9.1）。
   - v0.113.0 起不从 Windows 的 Steam 安装复制（那是直播在用的），改用 `tools/game_update/fetch_build.sh`：DepotDownloader 下到独立目录、摆好游戏文件与本地化、
     反编译、出新旧文件清单与反编译源码的初步对比；`tools/game_update/watch_steam.sh` 匿名定时查 Steam 各分支的版本（用法见脚本开头与 `游戏更新v0.113.0/适配报告.md` 第一节）。
   - 本机的版本归档（`~/.local/share/sls2/game-archive/`，决策记录 349 条一带）照做一份。
   - 租用机上用 `tools/remote/pack.sh` 按版本打包上传。
2. **改版本号，先编译**：

   ```bash
   printf 'v0.112.0\n' > engine/game_version.txt
   cd engine/Sts2Headless && dotnet build -c Release -o ../../.cache/eng-new 2>&1 | grep "error CS"
   ```

   - 编译错误就是游戏接口变了的地方：类被删、改名，方法签名、属性名变了。
   - 按第二节“接触面”改，改法写进提交说明。
   - 用 `typeof` 写的内容表，游戏删了牌也在这里报错。
   - **演练（v0.111.0 → v0.107.1 倒着编）**：25 个错误，都属于这一类：
     - `AssemblyInfo` 不可访问；
     - 随机数种子 uint / ulong；
     - `Rng.ToSerializable`、`RunRngSet.GetRng`、`CardPlay.Player` 不存在；
     - `Hook.ModifyDamage` 参数个数不同；
     - `Player.CanUseOrRemovePotions` 改名。

     当初升级到 v0.111.0 的提交 5be1cbe 也是这几类（药水接口改名、AssemblyInfo 初始化）。
3. **影响评估**：`python3 tools/game_update/update_impact.py --old v0.111.0 --new v0.112.0 --out 影响评估.md`（要先有新版的内容目录，见第 5 步；可以先做第 5 步再回来）。报告分三部分：
   - 内容目录的新增、删掉、改了，改了的列出变了哪些字段；
   - 引擎写全名引用的游戏类在新旧反编译源码里有没有变，连同引擎里引用它的位置（文件:行）；
   - 改了或删掉、引擎又按名字用到的条目（内容表命中）。

   重点复核后两部分：观测里按游戏代码写的算法（毒伤、刀刃陷阱、回合结束预演……）是否还对，补丁的参数是否还对。

   **演练（v0.107.1 → v0.111.0）**：
   - 内容目录新增 40、删掉 4、改了 439。目录格式本身多了升级后数值等字段，工具会单独说明、不算改动。
   - 引擎引用的游戏类变了 104 个。
   - 内容表命中 35 条。例如毒性爆发从能力牌改成了打全体的技能牌；放血改了稀有度；`Hook` 本身也变了。
4. **自检**：`dotnet .cache/eng-new/Sts2Headless.dll selfcheck 3`。
   - “缺”的逐个修：私有成员改名就改名字；补丁目标没了，要看游戏改成了什么，再决定补丁怎么改或者不再需要。
   - 按名字写的内容表、Boss 招式 ID 同样处理。
   - “新”的是新内容，下一步追加进词表；冒烟里的异常、卡住要查到根因。
5. **词表与内容目录**：
   - `dotnet .cache/eng-new/Sts2Headless.dll catalog`：把新内容追加到 `engine/catalog/vocab.txt` 末尾，旧 ID 不变；导出 `engine/catalog/<新版本>/catalog.json`。
   - 训练端载入检查点时，按检查点记录的词表大小把新增 ID 的嵌入行清零（决策记录里 v0.111.0 升级时加的机制）。
   - 内容先验按新目录重建。**特征列按名字对齐**（v0.113.0 起，`content.remap_columns`）：特征名按字母排序，新目录的新特征会插在中间，
     旧办法只在末尾补 0 会让老检查点的列整体错位而且不报错（v0.113.0 时 1,072 列里只剩 7 列对得上）。检查点存 `content_names`，旧检查点按列数在旧目录里算回来。

## 七、几条约定

- **游戏文件**：只放本机与租用机，不入库（决策记录第 5 条）。版本目录：`~/.local/share/sls2/game/<版本>/`，反编译：`~/.local/share/sls2/decompiled/<版本>/`。
- **词表**：只追加不重排。删掉的内容的 ID 留着不复用。
- **按名字找游戏成员**：一律经 `GameCompat`。新写的补丁用 `GameCompat.Patch`，新写的反射用 `GameCompat.Field / Property / Method`，并写清用途。
- **写死游戏规则**：尽量用 `typeof`（编译期就能发现删除），并写成角色文件里的表；只能按名字写的，在 `SelfCheck` 里登记核对。
- **观测的新内容**：一律加格式门控。正在训练、正在直播的角色的帧必须逐字节不变，用 `engine_equal.py` 证明。
