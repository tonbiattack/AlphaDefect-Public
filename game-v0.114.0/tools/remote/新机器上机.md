# 新机器上机清单（以 4090 机 B 为例）

从拿到 B 的地址到主线在 B 上开始训练的逐步操作。除特别说明外，命令都在本机仓库根目录（`~/dev/sls2`）运行；对 A 只做只读操作，A 上的训练全程不停。

B 的预期配置：i9-14900K（8 个性能核 + 16 个能效核，32 线程）、128 GB 内存、RTX 4090 24 GB，Ubuntu 22.04/24.04，root 登录。

| 步骤 | 做什么 | 预计耗时 |
| --- | --- | --- |
| 1 | 在 hosts.json 登记 B，确认能连上 | 5 分钟 |
| 2 | 打包上传，B 上运行 setup.sh | 15–30 分钟（主要是下载 PyTorch） |
| 3 | 从 A 的备份取一份检查点给基准测试用 | 3–5 分钟 |
| 4 | B 上运行 bench.sh | 10–12 分钟（`--quick` 约 5 分钟） |
| 5 | 选定硬件配置 | 5 分钟 |
| 6 | migrate.sh 把主线迁到 B 并启动 | 5–10 分钟 |
| 7 | 检查：开训 10 分钟、1 小时、24 小时 | — |

## 1. 登记 B

编辑 `tools/remote/hosts.json` 里的 `b`：填 `ssh_host`、`port`、`user`、`key`，删掉 `"pending": true`。

- 租用机的通讯都走伦敦跳转（用户 10-23 的要求）。在 `~/.ssh/config` 里给 B 的主机名加一条与 A 相同的 `ProxyCommand` 和连接复用（`ControlMaster`/`ControlPath`/`ControlPersist`）配置，hosts.sh 按 `ssh_host` 匹配这一条。
- B 只给了密码时，先把公钥装上：`ssh-copy-id -i ~/.ssh/KEY_RENTED.pub -p <端口> root@<地址>`。

检查：

```bash
bash -c '. tools/remote/hosts.sh; host_require b; $(host_ssh b) "hostname; nproc; free -g | head -2; nvidia-smi --query-gpu=name,driver_version --format=csv,noheader; cat /etc/os-release | head -1"'
```

预期：32 个逻辑核、约 125 GB 内存、`NVIDIA GeForce RTX 4090`。记下驱动版本：580 以上时 setup 会装与 A 相同的 CUDA 13.0 版 PyTorch；更低时会改装 cu128 版并给出警告（可以先请机房升级驱动）。

## 2. 打包上传与安装

```bash
SETUP=1 bash tools/remote/pack.sh b
```

pack.sh 打包工作区代码（含未提交改动，版本记在 `DEPLOY_INFO`）和本机 `~/.local/share/sls2/game/v0.111.0` 的游戏文件（约 40 MB），上传到 B 的 `/root/sls2-deploy/` 并解压，然后在后台运行 setup.sh。B 上已有部署时会拒绝覆盖（`FORCE=1` 可强制），训练正在跑时一律拒绝。游戏文件只传到自己的租用机，不要公开分发。

setup.sh 依次做：机器检查 → apt 补系统包（libicu、python3-venv、rsync、cron）→ 复制游戏文件 → 安装 .NET SDK 9.0.319（与 A 相同）→ 编译引擎 → 建虚拟环境，装 numpy 2.2.6、PyTorch 2.14.1（版本与 A 相同，PyTorch 的 CUDA 版本按驱动选）→ 冒烟测试 → 装定时任务（守护每 2 分钟、备份每 30 分钟）。运行目录为空时它会放一个 `STOP`，守护因此不会在迁移完成前从零开训；migrate.sh 放好检查点后会删掉它。

看进度：

```bash
bash -c '. tools/remote/hosts.sh; $(host_ssh b) "tail -f /root/sls2-deploy/setup.out"'
```

检查点（setup.out 里）：

- 出现“编译完成”“显卡计算正常”“训练代码可导入”；
- 冒烟测试 5 个角色各 5 局、`同种子一致：True`；`bench_async` 4 进程的吞吐应高于本机 i5-12600KF 的约 1,500 决策/秒；
- 最后一行是“下一步：基准测试”。末尾汇总的警告都要看：cgroup 不可写意味着评测无法限核，没有 `nvidia-cuda-mps-control` 意味着开不了 MPS，cron 没运行意味着守护和备份不会执行。

## 3. 给基准测试准备检查点

用 A 最近一次定时备份（只读，不碰 A 的训练），放到 B 的 `~/bench_ckpt.pt`：

```bash
bash -c '. tools/remote/hosts.sh; S=$(mktemp -d); fetch_ckpt a backup "$S" bench && rsync -a --partial -e "$(host_rsync_e b)" "$S/latest.pt" "$(host_addr b):bench_ckpt.pt" && rm -rf "$S"'
```

没有检查点时 bench 用随机初始化的网络，整局很快就死，对局分布与真实训练差得多，读数只能作参考。

## 4. 基准测试

```bash
bash -c '. tools/remote/hosts.sh; $(host_ssh b) "cd /root/sls2-deploy && setsid nohup bash sls2/tools/remote/bench.sh > bench.out 2>&1 < /dev/null &"'
bash -c '. tools/remote/hosts.sh; $(host_ssh b) "tail -f /root/sls2-deploy/bench.out"'
```

bench.sh 依次测：

1. 引擎：1 个引擎随机策略打战斗、整局各 15 秒；32 个引擎随机策略打战斗（只有引擎时的上限）。
2. 采集：默认 12×16、16×16、12×20、16×20 四个组合（采集进程 × 每进程引擎），用真实的采集进程和检查点推理，评测进程照常开着（SCHED_IDLE + cgroup 限核）。每个组合测两段：采集单独跑 20 秒；采集同时学习 25 秒（主进程在显卡上反复做与 train.py 相同的 PPO 更新，每次更新后照常发布权重）。决策数在采集进程里直接计数，不等对局结束。
3. 亲和性：在推荐组合上比较三种放法（见下文“大小核”）。
4. 学习单独跑：停掉采集与评测，测显卡独占时一次更新的耗时。

预计训练吞吐取 min(采集同时学习时的采集速度, 32,768 ÷ (学习一次的耗时 + 0.45 秒))，在最高值 3% 以内时选引擎较少的组合。某个组合显存或内存不够时，记下错误，跳过同一组里更大的组合。

结果在 B 的 `~/sls2-bench/<时刻>/`：`bench.log`（屏幕输出）、`bench.json`（全部读数）、`recommend_hw.json`（推荐的硬件项）。取回本机：

```bash
bash -c '. tools/remote/hosts.sh; $(host_ssh b) "cat \$(ls -1dt ~/sls2-bench/*/ | head -1)recommend_hw.json"' > /tmp/b_hw.json
```

读数时对照：

| 读数 | 对照值 | 说明 |
| --- | --- | --- |
| 单引擎·战斗 | 本机 i5-12600KF 约 340 决策/秒，A（v0.107.1）339 | 反映单核速度 |
| 学习用的数据里的 `macro_frac` | A 训练中约 0.13 | 明显偏低时，测出的学习耗时偏乐观 |
| 学习一次（采集同时） | A 上约 3.9–4.0 秒 | 4090 预计 2–3 秒 |
| 显存峰值 | 24 GB | 超过约 22 GB 就该减少采集进程数 |
| 内存 | 128 GB | 推荐时已为系统预留 12 GB |

## 5. 选定配置

`tools/remote/train_config.4090.json` 是事先写好的初始配置：A 在 2026-10-26 18:05 的 `train_config.json` 原样照抄，只改硬件项。迁移时只取硬件项（hosts.sh 的 `HW_KEYS`），训练目标、奖励、课程、批大小等一律跟随 A 的检查点配置，所以 B 上的主线与 A 完全一致。

| 项 | A | B 初始 | 依据 |
| --- | --- | --- | --- |
| `actors` × `envs_per_actor` | 12 × 16 = 192 | 16 × 16 = 256 | 见下 |
| `actor_device` / `learner_device` | cuda / cuda | 不变 | |
| `actor_threads` / `learner_threads` | 1 / 4 | 不变 | 采集推理在显卡上；学习进程的 CPU 线程只用于组批 |
| `infer_wait_ms` | 2.0 | 不变 | A 上试过 6 ms，没有收益 |
| `eval_workers` × `eval_envs` | 5 × 4 | 6 × 4 | 见下 |
| `eval_cpu_cores` | 5 | 6 | 见下 |

采集规模的估算：A 上 CPU 约 90%，其中 212 个引擎（含评测 20 个）合计约 17.7 核，12 个采集进程各约 0.87 核，学习进程约 1 核，吞吐约 6,000 决策/秒，所以 CPU 是瓶颈。按 A 的 Broadwell 超线程逻辑核折算，14900K 一个性能核的超线程约 2.8 个、一个能效核约 2.7 个，全机约 88 个，是 A（36 个）的约 2.4 倍；扣掉评测后，B 的采集上限约 1.3–1.4 万决策/秒。学习这边，A 上一次更新约 4.0 秒，按 4090 快 1.4–1.8 倍算是 2.2–2.9 秒，对应上限 1.1–1.4 万决策/秒，两边大致相当。B 的核更快，每个引擎来回一次更快，要喂满 CPU 需要的引擎比 A 多，初定 256 个。采集进程不超过 16 个：每个采集进程在显卡上约占 0.4 GB，A 上学习进程占约 15 GB，24 GB 显存放 16 个约用到 21.6 GB。内存按 A 的实测估：每个引擎约 0.23 GB，每个采集进程约 1.3 GB，256 + 24 个引擎合计约 90 GB（按 RSS 相加，有共享页，实际更少），128 GB 够用。

评测：A 上每轮 192 局约 215 秒，期间训练前进约 38 个版本。B 的版本推进预计快一倍左右；能效核约是 A 一个逻辑核的 2.7 倍，给 6 核、24 个引擎，每轮预计 1–2 分钟，按版本算的评测密度不低于 A，A、B 两条线按“分叉后同样多的版本”对比时，评测点一样密。代价是约 19% 的逻辑核，但评测以 SCHED_IDLE 运行，训练需要 CPU 时它会让路。

选择：

- bench 推荐的组合与初始配置的吞吐相差不到 5% 时，用初始配置：`--hw @tools/remote/train_config.4090.json`。
- 相差更多时，用 bench 的结果：`--hw @/tmp/b_hw.json`（评测三项来自 bench 读取的配置，也就是 train_config.4090.json）。最好同时把 `train_config.4090.json` 改成相同的值，留作记录。

## 6. 迁移主线

先预演（只读，打印计划）：

```bash
bash tools/remote/migrate.sh a b --dry-run --hw @tools/remote/train_config.4090.json
```

确认无误后执行。`--src fresh` 在 A 上先备份一次再取（不停 A 的训练），检查点最新：

```bash
bash tools/remote/migrate.sh a b --src fresh --hw @tools/remote/train_config.4090.json
```

migrate.sh 会：经本机中转复制检查点、配置、求解器标签、日志与评测记录、`best/`、`replays/`；把 B 原来的运行目录（setup 放的 STOP）改名留存；按 `--hw` 覆盖硬件项；核对检查点版本；删掉 STOP 并启动；把 `lines.json` 的主线改为 b。A 上原来的训练不停，之后要用 A 跑对照线时再用 fork.sh。

## 7. 开训后的检查

查看状态的命令（下文简称“看状态”）：

```bash
bash -c '. tools/remote/hosts.sh; $(host_ssh b) "R=~/.local/share/sls2/runs/defect; tail -2 \$R/train.out | cut -c1-400; cat \$R/status.json; echo; tail -1 \$R/resource.jsonl; tail -1 \$R/eval_progress.json 2>/dev/null; crontab -l"'
```

开训 10 分钟内：

- `train.out` 出现“从检查点继续：版本 ……”，版本号等于迁移时的版本（不是从 0 开始）。
- 256 个引擎同时启动约需 1 分钟（A 上 192 个要 60 多秒），之后每次更新打印一行。
- 跳过前 3 分钟后看 `sps`、`t_collect`、`t_learn`：`t_collect` 明显大于 0.5 秒说明采集是瓶颈，接近 0.3 秒、同时 `stale_steps` 增多说明学习是瓶颈。
- `resource.jsonl`：显存不超过约 22 GB，内存不超过约 110 GB。
- `eval_progress.json` 在走；第一条评测记录（`eval.jsonl`）应在 2–4 分钟内出现。

开训 1 小时内：

- `backups/` 里有了定时备份，`watchdog.json` 在更新。
- 本机拉取与看板能看到 B（拉取目录 `~/.local/share/sls2/runs/remote/defect-b`）。
- 吞吐稳定，不随时间下降。下降多半是 CPU 降频（14900K 满载约 250 W，机房散热不够会降频），可以在 B 上看 `grep MHz /proc/cpuinfo | sort -t: -k2 -n | head -3`。
- 需要调整时用 `bash tools/remote/restart.sh b '{"actors": 18}'` 一类命令（会先备份、再重启）。采集是瓶颈且 CPU 低于 90% 时加采集进程或每进程引擎；学习是瓶颈时减少引擎，降低过旧数据。

开训 24 小时内：

- `train.out`、`engine.log` 没有成批的引擎崩溃或采集进程报错；`dmesg | grep -i -E "mce|machine check|segfault"` 没有输出（见下文“风险”）。
- 评测成绩接上 A 迁移前的水平，没有断崖。

## 大小核与亲和性

14900K 的 32 个逻辑核分两类：8 个性能核（开超线程，一般是逻辑核 0–15）和 16 个能效核（没有超线程，一般是 16–31）。setup 与 bench 会从 `/sys/devices/cpu_core/cpus`、`/sys/devices/cpu_atom/cpus` 读出实际编号。

训练里对单线程速度最敏感的是学习进程（主线程发起显卡计算，后台线程组批）和采集进程（一个 Python 线程服务 16 个引擎，A 上每个都接近占满一核）；引擎是大量独立进程，看的是总算力。全部逻辑核都忙时，Linux 调度器主要按负载均衡，不会专门把这些关键线程留在性能核上，它们有一部分时间会落到能效核上，变慢约四成。

bench 在推荐组合上比较三种放法：

| 放法 | 学习与采集进程 | 训练引擎 | 评测 |
| --- | --- | --- | --- |
| none | 不绑定 | 不绑定 | 不绑定 |
| p | 性能核 | 不绑定 | 能效核 |
| pe | 性能核 | 能效核 | 能效核 |

建议：

- 默认不绑定。是否值得改，以 bench 的 p 相对 none 的结果为准：提高 5% 以上才值得做。
- pe 预计更差：能效核约占全机算力一半，而引擎要用掉约六成 CPU，把引擎全挤到能效核上会让性能核闲着。
- 若 p 值得做，实现方式有两种，都要改别的文件，由主会话决定：
  1. 新增一个定时绑核脚本（每分钟按进程树设置：学习与采集进程绑性能核，它们启动的引擎保持不限，评测进程树绑能效核）。不改训练代码，重启后一分钟内生效；采集进程重启引擎时，新引擎会继承采集进程的绑定，要由脚本下一轮改回。
  2. 改 `actor.py` 在启动引擎之后再把自己绑到性能核，改 `evaluator.py` 在已有的 `sls2-eval` cgroup 里加 `cpuset.cpus`（能效核）。改动小，但要重启训练。
- 只把评测放到能效核，就能避开 A 上实测过的问题（评测与训练争同一个物理核的超线程，训练慢 22%，决策记录第 50 条），因为能效核没有超线程。现有的 cgroup 限额（6 核）已经限住了评测的总量，所以这一项不急。
- 不要用 `taskset` 包住 start_train.sh：子进程（采集、引擎、评测）都会继承同一个绑定。

## 需要拿到 B 才能确认的

- 系统版本、驱动版本（是否 ≥ 580）、能否以 root 写 cgroup v2、是否有 `nvidia-cuda-mps-control`、cron 是否在运行（setup 都会检查并汇总警告）。
- 大小核编号是否就是 0–15 / 16–31，内核是否导出 `cpu_core` / `cpu_atom`（容器或虚拟机里可能没有，此时 bench 用 `--pe 0-15:16-31` 手动指定）。
- 实际吞吐、学习耗时、显存余量，以及 16×16 是否就是最优，以 bench 和开训后的日志为准。
- 机器是独占的物理机还是容器或虚拟机：容器里通常不能写 cgroup、不能开 MPS，`/dev/shm` 可能只有 64 MB。
- 从 B 能否顺利访问清华 PyPI 镜像（下载 PyTorch）和 dot.net（下载 .NET SDK）。

## 风险

- **14900K 的稳定性**：第 13、14 代酷睿在长时间高负载下有已知的电压与老化问题，表现为随机的段错误、非法指令、进程崩溃。上机后在 B 上看 `grep -m1 microcode /proc/cpuinfo`（应为 0x12b 或更新）；训练中引擎或 Python 进程无故崩溃、`dmesg` 有机器检查错误时，先怀疑硬件，请机房确认 BIOS 与微码，必要时用 Intel 默认功耗设置。
- **显存**：采集进程过多会挤爆 24 GB 显存，学习进程报显存不足后由守护重启，反复如此。bench 会记下失败的组合；开训后看 `resource.jsonl` 的 `gpu_mem_gb`。
- **降频**：满载功耗高，散热不够时吞吐会随温度下降，bench 只测十几分钟看不出来，要看开训后第一个小时的曲线。
- **bench 的偏差**：测试时间短，长的整局收到得少，学习数据里局外决策偏少，学习耗时可能偏乐观；随机初始化的网络偏差更大。所以开训后仍要按第 7 步的读数复核。
- **驱动低于 580**：只能用 cu128 版 PyTorch，与 A 的 CUDA 版本不同。数值上应无实质差别，但不再逐位一致；能升级驱动更好。

## 回退

迁移出了问题时，A 上的训练一直没停，主线可以留在 A：用 `bash -c '. tools/remote/hosts.sh; lines_set_main "{\"host\": \"a\"}" 迁移回退'` 把主线改回 A，再在 B 上 `touch ~/.local/share/sls2/runs/defect/STOP` 并停掉学习进程。B 上迁移前的运行目录被改名为 `defect.before-migrate-<时刻>`，没有删除。
