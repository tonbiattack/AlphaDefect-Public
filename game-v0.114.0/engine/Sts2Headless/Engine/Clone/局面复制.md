# 局面复制（原地快照）

无头引擎可以在任意决策点存下完整局面，之后反复恢复、接着往下走，包括恢复后再 reseed。用途有两个：搜索推演时，每个世界不再从头重放；训练时在线推演，在决策点分出若干条推演，推完回到原处接着打。

代码在 `engine/Sts2Headless/Engine/Clone/`，协议在 `Server.cs`。2026-11-16 起，分支 `engine-clone-v0.113.1`，游戏 v0.113.1。

## 一、为什么要做

原来引擎不能复制战斗状态。搜索时每个“世界”都要：

1. reset 开同一局；
2. replay 走一遍已经走过的动作；
3. reseed 换掉以后的随机数、重洗抽牌堆；
4. first 走要比较的候选；
5. 之后用模型推演。

本机实测（boss_pimc 负载，愚者第三幕双 Boss，6 个推演进程，CPU 推理，L1000，4 题 200 次搜索）：

| 项 | 耗时 |
|---|---|
| 一次搜索（32 个世界） | 平均 2.03 秒（最短 0.46，最长 6.84） |
| 每个世界的 reset | 4.6–5.4 ms |
| 每个世界的 replay（含 reseed 与首步） | 61–69 ms |
| 推演每步的 step / 取决策 / 编码观测 | 1.1 / 0.26 / 4.1 ms，平均约 11 步 |

一个世界的引擎开销约 128 ms，重放占一半。整局模式要从第一层重放，比这贵得多（直播接入.md：一次搜索平均 6.6 秒）。

## 二、可行路线与取舍

| 路线 | 结论 | 依据 |
|---|---|---|
| 游戏自己的存档 | 不行 | 存档 `SerializableRun` 不含战斗中途的状态，读档会从房间开头重打。联机重连带的 `NetFullCombatState` 只是生命、格挡、能力层数的摘要，用来核对是否失步；战斗回放 `CombatReplayWriter` 也是“开局存档 + 动作”。游戏自己就是靠重放来还原战斗的 |
| 进程级复制（fork） | 不行 | 实验：.NET 9 进程 fork 后，子进程分配内存时段错误（SIGSEGV）。默认设置、关掉并发 GC 与分层编译都一样：运行时的其他线程在子进程里不存在，GC 挂起线程时出错。CRIU 一类工具要 root 与内核支持，以磁盘镜像为单位存取，租用机上多半用不了 |
| 手写战斗状态的序列化 | 不选 | 要覆盖每张牌、每个能力与遗物的私有字段、怪物的招式状态机、挂起的回合循环。工作量大，每次游戏更新都要跟着改，正是“易于维护”要避免的 |
| 深拷贝成一套新对象 | 不选 | 恢复时要让所有静态根指向新对象。按身份散列的字典与集合要重建；只读静态字段不能改写（JIT 可能已当常量）；委托、闭包、挂起的 async 状态机都指向旧对象，要一一改指向，漏一处就错 |
| **原地快照** | **选用** | 拍快照时把每个可变对象浅拷贝一份；恢复时把字段原地写回原对象。对象身份不变，上面这些问题都不存在。代价是要定清楚“根”和“叶子”：漏记的可变状态恢复后会带着旧值。这由第五节的测试保证 |
| 只让重放更快 | 正交 | 复制之后，重放只剩推演进程跟随根局面时的一两步 |

## 三、设计

### 拍快照与恢复

- **根**：游戏（sts2.dll）与引擎程序集里已初始化类型的全部静态字段；服务端的会话状态（`ServeState`：当前局、当前决策、reset 时定下的开关、现场记录的 reset 原文与动作带）。
- **遍历**（`HeapWalker`）：从根出发，按身份去重，按类型取处理方式（`TypePlan`）。每个类型的“把引用字段交给遍历器”的代码用 IL 生成，沿结构体字段一路展开（字典的 `Entry[]` 之类的结构体数组也一样）。
- **记**：每个可变对象用 `MemberwiseClone` 浅拷贝一份，拷贝里的引用仍指向原对象。
  - 带终结器的对象（Godot 对象等），拷贝后 `GC.SuppressFinalize`。不然拷贝被回收时会释放与原对象共用的句柄：最初把 `WeakReference` 浅拷贝了，正则的替换缓存随即空引用，就是这个原因。
  - `ConditionalWeakTable`（引擎的“已知牌堆顶”与生物列表缓存在用）不浅拷贝，记下键值对，恢复时清空再放回。只存“键在别处也走得到”的条目：GC 还没回收的旧战斗牌堆不进快照，否则一份快照会从约 2,500 个对象涨到 65,000 个。
- **恢复**：IL 生成的逐字段写回（包括只读字段、各级基类的私有字段，引用字段经写屏障）；数组用 `Array.Copy`；可写的静态字段写回。只读静态字段不写，它们指向的对象内容已经原地恢复了。
- **前提**：拍快照时引擎停在决策点，消息泵空闲，只有主线程在跑游戏逻辑。服务端每个请求处理完时正是这个状态。

拍快照之后新建的对象，恢复后没有人再引用，由 GC 回收。快照本身只读，可以恢复任意多次；恢复之前进程走过别的路、甚至开过别的局，都不影响。

### 叶子（`ClonePolicy`）

叶子既不往下走，也不记。只有两类：

1. 与局面无关或不可变的运行时对象：字符串、反射对象及其数组与列表、流与编码器、线程与调度器、句柄、Harmony / System.Text.Json / 正则的内部对象（包括游戏里源生成的正则）、`WeakReference`、`ModelId`（不可变的记录）、特性、兼容层登记。
2. 游戏的模板：规范模型（`AbstractModel.IsCanonical`，玩的时候游戏自己断言不许改）、本地化表。

第 2 类是为了快，是否真的没被改由漏记审计核对（第五节）。到目前只查到四处模板被改，都是首次访问才生成的惰性缓存（`??=` 写法，值与时间线无关）：卡池的 `_allCards`、遗物池的 `_relics`、药水池的 `_allPotions`、规范能力的 `_dynamicVars`。

原则：宁可多记，不可漏记。多记只是慢一点，恢复写回的是同样的值。

### 类型的静态初始化（`TypeInit`）

读取静态字段本身会触发类型的静态初始化，而有的类型（`RichTextUtil`、`RichTextFadeIn` 等）的静态初始化会调 Godot 原生接口，无头下进程直接退出（`GodotShim.Trap`，退出码 97）。所以：

- 只取已经初始化的类型。.NET 没有公开接口判断这一点，这里读 CoreCLR 的 MethodTable：偏移 32 是辅助数据指针，标志位 0x1 表示已初始化、0x100 表示初始化出错（dotnet/runtime 9.0 的 methodtable.h；System.Private.CoreLib 的 `MethodTable` 结构里也是这个偏移）。第一次用之前拿一个专用的哨兵类型核对（初始化前读到“否”、初始化后读到“是”），对不上就拒绝拍快照，免得换了运行时版本后静默地判错。
- 没初始化的类型不去初始化。拍快照之后才初始化的类型记进 `CloneRoots.LateInit`，下次拍快照时补进根。v0.113.1 测到的晚初始化类型只有常量表（颜色、怪物组合、偷牌优先级的委托数组等）与编译器生成的委托缓存（`<>c`、`<>O`），不影响局面。clone-test 会把“有可写静态字段”的晚初始化类型单独标出来。

### 局限

- 快照只在本进程内有效，不能序列化，也不能跨进程或跨机器传。每个推演进程都要自己先到达根局面（第一次重放一次，之后跟随，见第四节）。
- 内存：战斗模式每份快照约 2,000–3,000 个对象，整局模式约 3,000–5,000 个。槽位由调用方管，用完 `drop`。

## 四、协议

| 请求 | 作用 | 回复 |
|---|---|---|
| `{"op":"snapshot","slot":0}` | 把当前局面（上一个回复之后的样子）存进槽位 | UTF-8 JSON `{"slot","objects","ms"}` |
| `{"op":"restore","slot":0}` | 恢复到槽位里的快照 | 观测帧 |
| `{"op":"restore","slot":0,"replay":[..],"branch":7,"reseed":5,"first":2}` | 恢复后再走，语义同 reset 的同名项 | 观测帧 |
| `{"op":"drop","slot":0}` / `{"op":"drop"}` | 丢掉一个槽位 / 全部 | UTF-8 JSON `{"dropped","slots"}` |
| 任何返回帧的请求带 `"snapshot":k` | 回复之后把这时的局面存进槽位 k | 照常 |
| 任何返回帧的请求带 `"auto_single":true` 或整数 N | 只有一个候选的决策由引擎自己走过（整数时最多 N 步） | 帧尾附加信息里 `auto_steps` 为走了几步 |
| reseed 带 `"keep_top":true` | 已知的抽牌堆顶不洗（见第七节） | 照常 |

restore 带的 `replay`、`branch`、`reseed`、`first` 会记进现场动作带（卡住日志的“reset 原文 + 动作带”照样能复现恢复后的局面）。
reset 的 `first` 只跟着 `reseed` 或 `branch` 生效（老语义不变）；restore 只带 `first` 时也走这一步。

快照是“上一个回复之后的样子”，所以 reset 带 `"snapshots":true` 时，帧尾的“这场战斗刚开始”（`combat`）、开幕信息只出现在原来那一帧：
在战斗第一帧拍快照、恢复后再编的同一帧不再带它们（观测本身逐字节相同）。训练采集据此记一场战斗开始，恢复后不重复记，是想要的行为。
反过来，reset + replay 重放到战斗中途时，第一帧会自称“战斗刚开始”——这是重放路径原有的现象。clone_fidelity 把这两种附加信息的差别单独统计，不算不同。

典型用法：

- **PIMC 的世界**：`{"op":"restore","slot":0,"reseed":s,"first":c}`，之后照常 step。和原来的 `reset + replay + reseed + first` 同形，一次往返。
- **推演进程跟随根局面**：第一次 `reset + replay` 到根并带 `"snapshot":0`；之后每次新的根，`{"op":"restore","slot":0,"replay":[实机新走的几步],"snapshot":0}`。不再从头重放。
- **训练时在线推演**：采集进程在决策点 `snapshot`，分出 K 条推演，每条 `restore + reseed + first` 后往下走，推完 `restore` 回来，接着走真实的动作。

## 五、验证

| 工具 | 查什么 |
|---|---|
| `clone-test roundtrip [combat\|run] 局数 步数 [角色]` | 同一进程：在随机一局里均匀抽一个决策点拍快照 → 走 A（一半先 reseed）→ 恢复照走 A → 恢复走另一条路 → 恢复再照走 A → 恢复比根帧，逐字节比较 |
| `clone-test audit [combat\|run] 局数 步数` | 漏记审计：同一处各拍一份“全记”（叶子也往下走）与正式快照，走若干步后查“被改过、却不在正式快照里”的对象；只有模板的惰性缓存才算通过 |
| `clone-test bench 题目.json 题数 世界数` | 引擎侧测速：复制对重放，帧逐字节核对，重开别的局后再恢复核对 |
| `clone-test census [combat\|run] 局数` | 快照规模、按类型与程序集分布、静态根、晚初始化的类型、拍与恢复的稳态耗时 |
| `tools/clone/clone_fidelity.py` | 跨进程验收：复制路径（restore + reseed + first）与重放路径（reset + replay + reseed + first）逐字节比较，跳过随进程累计的头部 12、14 |

两条经验：

- **随机局覆盖不到的局面要专门构造。** 环境变量 `CLONE_TEST_DECK="卡牌*张数,..."` 指定牌组。弱引用表漏记的问题，在随机牌组的 120 局储君、愚者往返里一次都没碰到（拍快照时抽牌堆顶有已知牌的局数为 0）；换成专放牌堆顶的牌组，80 局里有 35 局碰到。
- **反向核对**：`STS2_CLONE_WEAK_LEAF=1` 让引擎退回把弱引用表当叶子的旧写法，同样的语料应当报出不同（储君 35 局全部报出）。证明测试抓得住这类问题。

## 六、游戏更新时怎么维护

照《引擎模块与游戏更新适配》第六节走完之后，加做：

1. `clone-test census combat 6` 与 `census run 4`：看静态初始化失败、晚初始化的类型（尤其标了“有可写静态字段”的，要对照反编译源码确认只是常量或缓存）、快照规模有没有异常变化。如果第一次拍快照就以退出码 97 退出，说明某个类型的静态初始化碰了 Godot 原生接口，而我们去初始化了它：看日志里的调用栈，在 `ClonePolicy.SafeToInitialize` 一带处理（现在不主动初始化任何类型，正常不会出现）。
2. `clone-test roundtrip combat 60 40`、`roundtrip run 24 60`，以及针对性牌组（放牌堆顶、召唤、充能球、能力多的牌组）各几十局：不同必须为 0。
3. `clone-test audit combat 60 40`、`audit run 24 80`：只允许模板的惰性缓存。出现新的非惰性改动，就是有新的可变状态挂在叶子后面，在 `ClonePolicy` 里把对应的类型从叶子里拿掉。
4. `tools/clone/clone_fidelity.py` 大样本跨进程验收。
5. 换 .NET 运行时大版本时，`TypeInit.Validate` 会在第一次拍快照时核对 MethodTable 的读法，对不上就报错。照新版 methodtable.h 改偏移与标志位。

要改的地方集中在 `ClonePolicy.cs`（叶子、根、哪些类型能初始化）与 `TypeInit.cs`（运行时内部布局）。游戏规则本身的变化不用管：快照记的是游戏对象的字段，不关心它们的含义。

## 七、可选开关与没做的事

- `auto_single`（推演用）：只有一个候选的决策由引擎自己走过，不编码、不回 Python，省掉这些帧的编码与网络前向。核对：36 场战斗里，带开关的进程与逐步走（单候选走第 0 个）的进程在多候选决策上 551 帧逐字节相同，自动走的步数与对照进程见到的单候选帧数相同（100）。
  推演要保持“走 leaf 步后估值”的口径时传整数上限 N = leaf − 已收帧数 − 1（boss_pimc 的 `--auto-single` 就这样做），自动走不会越过估值的那一帧；只传 true 时，若第 leaf 步本是单候选帧会被一并走过（子智能体实测约 4% 的世界）。
- `keep_top`：reseed 时已知的抽牌堆顶（被效果明确放到顶部、玩家知道位置的那一段，`Observation.DrawTop.Known`，观测格式 20 起编进帧里的同一份）不洗，只洗下面。解决直播接入.md 写的已知局限。它会改变推演世界的分布，开不开由使用者决定。核对：储君放牌堆顶的牌组 691 个局面，两个种子 reseed 后顶部的公共前缀合计 460 张（不保留时 97 张，是同名牌碰巧在顶部）。
- **范围化快照（只恢复战斗中会变的部分）：测了，没做。** 走 12 / 20 / 40 步后，快照里被改过的对象只占 3.6% / 3.9% / 4.0%。只写回这部分，每个世界最多省约 0.3 ms，不到推演开销的 0.5%，却要冒漏记的风险。
- **GC 参数：测了，不改。** C 机空闲时用 `clone-test bench` 两轮对照：默认设置每个世界 11.5–11.6 ms（复制路径），gen0 预算 256 MB 为 11.7–13.8 ms，关并发 GC 为 12.1–12.3 ms。默认最好。
